# Language (English + French)

Two locales, `en` and `fr`. Decided by roadmap D8; the reasoning for stopping at
these two, and for what stays English, is there. This spec is the "how".

## 1. Where the locale comes from

Detected from the browser, not the server — there is no per-request rendering
for a game page, and the hub's own request-time step (`api/index.php`
splicing flags into a build-time shell, [seo.md](seo.md) §4) never looks at
headers either, so a server-side decision would be new machinery for its own
sake. `detectLocale()` (`www/src/core/i18n/locale.ts`) reads
`navigator.languages`, matches the first tag whose primary subtag is `en` or
`fr`, and falls back to English for anything else — Spanish, German, a
malformed tag, an empty list.

Overridden by the picker (§3) and remembered in `localStorage` under
`fony:locale`, on the same lifetime as `core/profile.ts`'s name/avatar: it is
a fact about the device, survives closing the tab, and is never sent to the
server.

`LocaleProvider` (`www/src/core/i18n/LocaleContext.tsx`) resolves all of this
once, in a `useState` initializer that runs before the first paint, and
exposes it as `useLocale()`. It is mounted once per page — `www/src/main.tsx`
for the hub, each `www/src/<slug>.tsx` for a game — the same point every page
already renders from.

## 2. What is translated, and how

**Shared chrome** — the hub, the room/join picker, the lobby, and the pieces
they're built from (`lobby/parts.tsx`, `core/ui/JoinByCode.tsx`) — lives in
`www/src/core/i18n/strings.ts`: one `UiStrings` interface, one `en` and one
`fr` implementation, read through `useT()`. English is not a fallback here —
both are complete, since this is a small, closed set of strings that changed
once, deliberately, rather than per-game content that grows one file at a
time.

**Each game's card** (title, pitch, concept, rules, art alt text) works
differently, because `card.ts` is a leaf file games add one at a time
(`www/src/games/cards.test.mjs` enforces its narrow import list) and a
translation can lag behind a new game shipping. `GameCard` carries an
optional `fr` block next to the English fields:

```ts
fr?: {
  title?: string;
  pitch?: string;
  concept?: string;
  rules?: string[];
  art?: { alt?: string };
};
```

`localizeCard(card, locale)` (`www/src/core/i18n/localizeCard.ts`) merges it
over the English card field by field — a game can ship with only some fields
translated, and an untranslated one falls back to English rather than
leaving a blank. **Title is deliberately never translated**: it is the
game's name, the same reason `FonyGames` itself never becomes anything else.
A rule string keeps `HowToPlay.tsx`'s `{{#hex|word}}` colour markup verbatim
in French — the markup names a hex colour, not a word to translate, and
Grid Attack's French rules use it exactly as the English ones do
(`www/src/games/grid-attack/card.ts`).

`localizeCard` is called in exactly two places, both funnels that already
existed: `HubGrid` (one call per card, for the hub's grid) and `RoomGate`
(one call per room, which then hands the localized card to `RoomChoice`,
`NoSuchRoom`, and — via a widened render-prop, `(code, card) => …` — to
every game's own room component). Nothing downstream of either funnel
needs to know translation exists at all.

## 3. The picker

`core/ui/LocalePicker.tsx`: one button (`EN`/`FR`, not a flag — English has
no single national flag), top-right on the hub, the room/join picker and the
lobby. Opens a `Sheet` (the same shell `ProfileSheet` uses) listing "English"
/ "Français" — each named in itself, not translated, so a player stuck on
the wrong language can still recognise their own to tap it. Picking one
calls `setLocale`, which persists and re-renders immediately.

The three headers (`hub.css` `.hub__header`, `lobby.css` `.lobby__header` and
`.choice__header`) reserve the corner with `position: relative` and a
`padding-right` sized to the button, rather than becoming flex rows — none of
the three had a reserved corner before, and this way the existing
back-link/title/pitch stack is untouched.

## 4. What stays English, and why

- **SEO `<meta>`, OG tags, JSON-LD** — generated once at build time per
  [seo.md](seo.md) §4; the language switch is a client-side, post-load
  effect, and a search engine or a link preview never runs it. Serving a
  French variant would mean a second build artifact and PHP-side language
  negotiation — a real architectural fork, and its own decision.
- **The admin tool** (`www/src/ops.ts`) — one operator, not a player surface.
- **Worker and API error text** (`worker/Room.ts`, `worker/index.ts`,
  `api/*.php`) — small, rare, edge-case strings (a full room, a dropped
  socket, a missing database) rather than anything a round is played
  through.
- **`shared/names.ts`'s avatar word bank** — a name generator, language-
  neutral by design rather than by omission.

## 5. Adding a translation to a new game

Add an `fr` block to the game's `card.ts` (§2) alongside its English fields.
Nothing else changes — no new file, no import, no component to touch. If a
rule uses the `{{#hex|word}}` markup, keep the markup and translate the word
inside it.

## 6. Verification

`www/src/core/i18n/i18n.test.ts` (`npm run test:i18n`) covers `detectLocale`
against realistic tag lists and `localizeCard`'s per-field fallback. Browser
verification: a Chromium context with `locale: 'fr-FR'` against `vite` +
`wrangler dev` shows French chrome and French card content on the hub, the
room/join picker and the lobby; the picker switches locale immediately and
the choice survives a reload.
